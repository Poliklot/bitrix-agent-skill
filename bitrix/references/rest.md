# Bitrix REST API — core-first справочник

> Reference для Bitrix-скилла. Загружай, когда задача связана с `rest`, `OnRestServiceBuildDescription`, `CRestServer`, исходящими REST-событиями, `event.bind`, placement'ами или серверной регистрацией REST-методов. Для shop-core sale/catalog REST controllers, webhooks/events/placements and `webservice`/SOAP integration extras сначала открывай `shop-integrations-webservice.md`.

## Область применимости новых контрактов

K21–K38 и K40 ниже — внешнее REST API и приложения **Битрикс24** по официальной документации, не подтверждение наличия этих возможностей в любом 1С-Битрикс: Управление сайтом. Сначала установи продукт, модуль, версию REST, способ авторизации и доступность метода. Не переноси облачные ограничения, BX24.js или REST 3.0 на локальное CMS-ядро автоматически. Исторический core-аудит ниже не распространяется на новые documentation-backed дополнения.

## Что подтверждено в текущем core

- Точка входа методов собирается через событие `rest:OnRestServiceBuildDescription`.
- Описание сервисов агрегирует `CRestProvider::getDescription()`.
- Базовый сервер запросов — `CRestServer` из `www/bitrix/modules/rest/classes/general/rest.php`.
- Специальные ключи описания:
  - `CRestUtil::GLOBAL_SCOPE` = `_global`
  - `CRestUtil::EVENTS` = `_events`
  - `CRestUtil::PLACEMENTS` = `_placements`
- Исключения REST — `Bitrix\Rest\RestException`.

## Регистрация методов

```php
use Bitrix\Main\EventManager;

EventManager::getInstance()->addEventHandler(
    'rest',
    'OnRestServiceBuildDescription',
    ['\\MyVendor\\MyModule\\RestService', 'onBuildDescription']
);
```

Для постоянной регистрации в install-логике модуля тоже допустим `registerEventHandler(...)`.

## Формат описания

```php
use CRestUtil;

class RestService
{
    public static function onBuildDescription(): array
    {
        return [
            'my_scope' => [
                'my.item.list' => [__CLASS__, 'itemList'],
                'my.item.get' => [
                    'callback' => [__CLASS__, 'itemGet'],
                    'options' => [],
                ],
                CRestUtil::EVENTS => [
                    'OnMyItemAdd' => [
                        'my.module',
                        'OnAfterMyItemAdd',
                        [__CLASS__, 'onItemAdd'],
                        [
                            'sendAuth' => true,
                        ],
                    ],
                ],
                CRestUtil::PLACEMENTS => [
                    'MY_WIDGET' => [
                        'private' => true,
                    ],
                ],
            ],
            CRestUtil::GLOBAL_SCOPE => [
                'my.server.time' => [__CLASS__, 'serverTime'],
            ],
        ];
    }
}
```

### Что важно про сборку описания

- `CRestProvider` делает `array_merge_recursive(...)` для всех обработчиков `OnRestServiceBuildDescription`.
- Имена методов и scope затем приводятся к нижнему регистру.
- Ключи внутри `_events` и `_placements` приводятся к верхнему регистру.

## Сигнатура callback

Текущий core вызывает callback так:

```php
public static function itemList(array $query, int $start, \CRestServer $server): array
{
    $authData = $server->getAuthData();
    $userId = (int)($authData['user_id'] ?? 0);
    $clientId = (string)($authData['client_id'] ?? '');

    $items = [];
    $total = 0;

    return [
        'items' => $items,
        'total' => $total,
    ];
}
```

### Поведение `CRestServer::processCall()`

- параметр `start` берётся из `$query['start']`, затем удаляется из входного массива;
- callback получает `($query, $start, $server)`;
- если callback вернул массив с `next` и `total`, сервер выносит их на верхний уровень ответа;
- итоговый успешный JSON строится как `['result' => ..., 'next' => ..., 'total' => ...]`.

## `CRestServer`: что брать откуда

```php
$server->getAuthData();   // полные auth-данные провайдера
$server->getAuthScope();  // scope из authData['scope']
$server->getClientId();   // CLIENT_ID приложения
$server->getMethod();     // текущее REST-имя метода
$server->getScope();      // найденный scope текущего метода
$server->setStatus(\CRestServer::STATUS_CREATED);
```

### Важная разница: `getAuth()` vs `getAuthData()`

- `getAuthData()` — основной источник auth-метаданных (`user_id`, `client_id`, `scope`, `auth_connector`, `parameters` и т.д.).
- `getAuth()` не равен полному auth payload; туда попадают только параметры, которые auth-провайдер вынес из входного query через `parameters_clear`.

Если нужен `user_id`, в текущем core безопаснее брать его из `getAuthData()`, а не из `getAuth()`.

## Ошибки

```php
use Bitrix\Rest\RestException;

throw new RestException(
    'ID обязателен',
    RestException::ERROR_ARGUMENT,
    \CRestServer::STATUS_WRONG_REQUEST
);
```

Подтверждённые коды в core:

- `ERROR_ARGUMENT`
- `ERROR_NOT_FOUND`
- `ERROR_CORE`
- `ERROR_OAUTH`
- `ERROR_METHOD_NOT_FOUND`
- `ERROR_OPERATION_TIME_LIMIT`

Подтверждённые HTTP-статусы в `CRestServer`:

- `STATUS_UNAUTHORIZED`
- `STATUS_FORBIDDEN`
- `STATUS_NOT_FOUND`

## Исходящие события и `event.bind`

Серверные `_events` в описании метода только объявляют доступные события. Реальная отправка наружу происходит после `event.bind`.

Что проверено в `Bitrix\Rest\Api\Event`:

- `event.bind` требует OAuth-auth type;
- для offline-ивентов нужны права администратора;
- `EVENT` приводится к верхнему регистру;
- `EVENT_TYPE` поддерживает `online` и `offline`;
- для `online` обязателен `HANDLER`;
- для событий с опцией `disableOffline => true` offline-регистрация запрещена.

Пример обработчика исходящего события:

```php
public static function onItemAdd(\Bitrix\Main\Event $event): array
{
    $fields = $event->getParameter('fields');

    return [
        'data' => [
            'FIELDS' => [
                'ID' => $fields['ID'] ?? null,
            ],
        ],
    ];
}
```

## Placement и userfieldtype

В текущем core есть отдельный REST API для пользовательских UF-type placements:

- `Bitrix\Rest\Api\UserFieldType`
- scope: `placement`
- placement code: `USERFIELD_TYPE`

Если задача про REST-встраивание UF-типа, сначала смотри `rest/lib/api/userfieldtype.php`, а не общие примеры из памяти.

## Gotchas

- `OnRestServiceBuildDescription` вызывается на каждом REST-запросе: handler должен быть лёгким.
- Не полагайся вслепую на `$server->getAuth()['user_id']`: в текущем core надёжнее `$server->getAuthData()['user_id']`.
- `_events` и `_placements` после сборки нормализуются по регистру, поэтому не завязывайся на исходный case.
- `RestException::__construct()` принимает строковый error code, но PHP exception code внутри всё равно приводится к `int`; для логики REST смотри `getErrorCode()`, а не `getCode()`.
- `event.bind` валидирует callback через `HandlerHelper::checkCallback(...)`, поэтому внешний URL надо проверять по реальному app context.

## K21 — Пакет REST не является транзакцией

Для классического `batch` передавай до 50 команд, не вкладывай `batch` в `batch`. Зависимости задаются через `$result[имя][поле]`; имя команды сохраняй для сопоставления ответа. Разбирай `result.result` и непустой `result.result_error`, а не только HTTP 200. `halt=1` прекращает дальнейшие команды после ошибки, но не откатывает выполненные; `halt=0` продолжает обработку. Архитектурное следствие: сохраняй результаты отдельных операций и повторяй только нужные команды после сверки состояния, не весь пакет создания объектов. Правила REST 3.0 отличаются (K23).

**Проверка на стенде:** Три команды на тестовых данных: успех, ошибка, успех; сравнить halt=0/1 и отсутствие дубля при восстановлении.

[Официальный контракт](https://apidocs.bitrix24.ru/settings/how-to-call-rest-api/batch.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K22 — Постраничная REST-выгрузка и условие завершения

У классического списочного метода бери следующую позицию из `next` ответа и передавай её в `start`. Завершение — отсутствие `next`, а не размер текущего массива и не обещанное `total`: подсчёт может отсутствовать. Структуру `result` бери из конкретного метода (`items` и плоский список не взаимозаменяемы). Сохраняй неизменные фильтр и сортировку между страницами. Для изменяющихся данных это не snapshot: проектный checkpoint, дедупликация по ID и сверка изменений нужны отдельно; ID-based обход используй только при поддерживаемых фильтре/сортировке.

**Проверка на стенде:** Выборка на несколько страниц без total: все ID прочитаны; вложенный items не принят за одну запись.

[Официальный контракт](https://apidocs.bitrix24.ru/settings/how-to-call-rest-api/list-methods-pecularities.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K23 — Версия REST определяется маршрутом и схемой метода

В Битрикс24 классический REST и REST 3.0 сосуществуют. Наличие метода в одном варианте не означает наличие в другом. У REST 3.0 путь содержит `/rest/api/`; не меняй только URL у старого клиента — проверь параметры, тело, ответ и поддержку версии используемой библиотекой. Один метод может иметь разные схемы в двух версиях. Для нового сценария выбирай поддерживаемую версию конкретного метода по её документации; отсутствующий метод не заменяй похожим именем и не объявляй поломкой токена без проверки маршрута.

**Проверка на стенде:** Для одного метода сравнить обе страницы контракта и маршруты; отсутствующая версия даёт контролируемый отказ.

[Официальный контракт](https://apidocs.bitrix24.ru/api-reference/). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K24 — Входящий вебхук наследует права владельца

Входящий вебхук выполняет вызовы от своего создателя в пределах выбранных scope. Scope не предоставляет владельцу отсутствующие права на объект. Разделяй ошибку недостаточного scope и отказ доступа пользователя; проверяй оба слоя, не выдавай администраторские права как универсальный ремонт. URL содержит секретный код: серверное хранение и редактирование логов обязательны, его нельзя помещать в публичный JS. Методы, которым нужен контекст приложения, не становятся доступными от замены OAuth-токена URL вебхука.

**Проверка на стенде:** Одна доступная и одна запрещённая владельцу запись; доступы и секретный URL не утекли в клиент.

[Официальный контракт](https://apidocs.bitrix24.ru/first-steps/first-rest-api-call.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K25 — Продление OAuth без гонки между обработчиками

Сохраняй пару `access_token`/`refresh_token`; при `expired_token` обнови её и повтори исходный вызов с новой парой. Не делай refresh перед каждым запросом и не лечи им любые 401/403. Проектный инвариант поверх протокола: один обновляющий процесс на запись авторизации (приложение, портал, пользователь), атомарная замена пары и повторное чтение после ожидания блокировки. Иначе параллельный обработчик перезапишет свежие данные устаревшими. Ограничь число повторов; при неустранимой авторизационной ошибке останови операции и запроси восстановление доступа, а не запускай бесконечный refresh.

**Проверка на стенде:** Два конкурентных потребителя одной пары: один refresh, оба используют сохранённую пару; постоянная ошибка останавливает цикл.

[Официальный контракт](https://apidocs.bitrix24.ru/settings/oauth/auto-renewal.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K26 — Портал идентифицируется member_id, а не доменом

При переезде Битрикс24 сохраняется `member_id`. Храни принадлежность установки по нему (и ID приложения), а актуальный `client_endpoint` — отдельно и обновляй из проверенных авторизационных данных. Не используй домен как постоянный ключ данных клиента и не путай `client_endpoint` с адресом сервера авторизации. Отдельного REST-события переезда нет. Защита границы интеграции: неподтверждённый POST с новым endpoint не должен менять адрес отправки секретов; проверяй источник и разрешённый HTTPS-адрес, включая собственные домены/коробку по конфигурации установки.

**Проверка на стенде:** Проверенная смена домена сохраняет клиента; поддельный endpoint отклонён до исходящего запроса.

[Официальный контракт](https://apidocs.bitrix24.ru/settings/how-to-call-rest-api/change-domen.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K27 — Проверка подлинности REST-события

До обработки события найди сохранённый `application_token` по `auth.member_id` и установке приложения, затем сравни секрет с входящим (в серверном коде — безопасным сравнением). Отсутствие/несовпадение — отказ без side effects. Первое сохранение на `ONAPPINSTALL` требует проверки полученной авторизации; не доверяй произвольному install POST. На доверенном `ONAPPUPDATE` учитывай обновление токена. В `ONAPPUNINSTALL` рабочей авторизации уже нет: нельзя заменять проверку application_token попыткой REST-вызова. Для исходящего вебхука секрет берётся из его настроек, это не код входящего вебхука.

**Проверка на стенде:** Верный, отсутствующий и чужой токены; только верный вызывает согласованный обработчик, без записи секретов в журнал.

[Официальный контракт](https://apidocs.bitrix24.ru/api-reference/events/safe-event-handlers.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K28 — Офлайн-очередь не является журналом всех изменений

Офлайн-событие содержит `EVENT_DATA` и ключ `MESSAGE_ID`, рассчитанный из события и данных. Повтор с тем же ключом обновляет запись, а не создаёт независимую историческую запись. Поэтому очередь служит сигналом перечитать актуальное состояние, а не восстановить каждый промежуточный переход. Для удаления предусмотрен отдельный сценарий отсутствующего объекта. Если нужен аудит всех изменений, согласуй отдельный источник истории: число записей очереди не равно числу бизнес-операций. Не создавай цикл «событие → безусловный update того же объекта → событие».

**Проверка на стенде:** Несколько обновлений одного объекта до чтения: итог синхронизирован, промежуточная история не выдумана.

[Официальный контракт](https://apidocs.bitrix24.ru/api-reference/events/offline-events.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K29 — Получение офлайн-событий по умолчанию удаляет их

`event.offline.get` по умолчанию использует `clear=1`: получение уже удаляет записи. Для восстановления после сбоя явно выбирай поддерживаемый `clear=0`, сохраняй полученный `process_id`, обрабатывай и отдельно подтверждай. Контекст приложения, права и доступность `rest_offline_extended` обязательны; нельзя молча перейти на разрушающий режим при отказе тарифа. Повторное чтение пакета также делай с `clear=0`: сочетание `process_id` и `clear=1` удаляет весь пакет, даже когда `limit` вернул лишь часть. Это не безлимитное надёжное хранилище: учитывай срок хранения платформы и план восстановления.

**Проверка на стенде:** На отдельной тестовой очереди упасть после резервирования и повторно получить тот же пакет без удаления.

[Официальный контракт](https://apidocs.bitrix24.ru/api-reference/events/event-offline-get.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K30 — Подтверждение офлайн-пакета имеет опасные пустые значения

Перед `event.offline.clear` требуй непустой `process_id` из собственной сохранённой квитанции и тот же `auth_connector`, если он применялся. Пустой process_id может удалить все незарезервированные записи приложения, а не вернуть ошибку. При частичном успехе передавай только подтверждённые `message_id` (либо ID согласно контракту); пустой/пропущенный список означает весь пакет. Поэтому если успехов нет — пропусти clear, а не отправляй пустой массив. `message_id` имеет приоритет над `id`. Подтверждай лишь после устойчивой фиксации результата получателем.

**Проверка на стенде:** Контроль запроса до отправки: ноль успехов не вызывает clear; частичный успех не удаляет оставшиеся записи.

[Официальный контракт](https://apidocs.bitrix24.ru/api-reference/events/event-offline-clear.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K31 — Повторная обработка ошибочных офлайн-событий

`event.offline.error` принимает `message_id` из поля `MESSAGE_ID`, не числовой `ID` объекта или очереди. Помеченные записи снимаются с резерва и выбираются через `event.offline.get(error=1)`, не обычным чтением. Проверяй принадлежность ключей и `process_id` своей квитанции до вызова: неверный/чужой пакет способен удалить незарезервированные записи с теми же ключами и вернуть true. Пустой массив message_id также возвращает true без изменения. Успех метода не доказывает, что нужная запись помечена; сверь очередь и организуй ограниченный повтор ошибочной ветки.

**Проверка на стенде:** На выделенной очереди один корректный ключ попадает в error=1; неверные квитанции отвергаются локально до API.

[Официальный контракт](https://apidocs.bitrix24.ru/api-reference/events/event-offline-error.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K32 — Лимиты частоты и ресурсоёмкости REST различаются

Различай `QUERY_LIMIT_EXCEEDED` (интенсивность) и `OPERATION_TIME_LIMIT` (накопленная стоимость конкретного метода). Для первой ошибки снижай частоту и ограничивай параллелизм; для второй учитывай `time.operating` и `operating_reset_at`, уменьши выборку/стоимость метода. Reset не обязан обнулить operating: окно состоит из нескольких временных корзин. Числовые пределы зависят от облака/коробки и конфигурации — не закрепляй единую вечную норму запросов. Проектная стратегия: ограниченный backoff с разбросом и бюджетом попыток; остановка при устойчивой блокировке. Batch не отменяет ресурсоёмкость вложенных методов.

**Проверка на стенде:** Ошибки обеих категорий запускают разные ограниченные стратегии; исчерпание бюджета завершает попытки.

[Официальный контракт](https://apidocs.bitrix24.ru/settings/performance/limits.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K33 — Файловое поле REST не равно объекту Диска

Перед загрузкой определи тип поля и метод: строка Base64, пара имя/контент, `fileData` и `fileContent` не являются универсально взаимозаменяемыми. Для поля, связанного с Диском, часто сначала загружают объект Диска, затем прикрепляют его ID; некоторые методы делают оба шага сами. Не путай ID объекта Диска с его `FILE_ID` и идентификатором привязки. Успешное создание бизнес-объекта может вернуть ID объекта, а не загруженного файла — получи файловые данные последующим чтением. Не отправляй локальный путь сервера вместо содержимого.

**Проверка на стенде:** Обычное файловое поле и привязка к Диску читаются обратно с правильными ID и ожидаемым содержимым.

[Официальный контракт](https://apidocs.bitrix24.ru/api-reference/files/how-to-upload-files.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K34 — Готовность BX24.js не равна готовности DOM

В интерфейсе приложения выполняй чтение контекста и REST-операции после `BX24.init(callback)`: библиотека должна получить данные от родительской страницы Битрикс24. `DOMContentLoaded` сообщает только о DOM и не заменяет этот обмен. До инициализации `BX24.getAuth()` и `BX24.isAdmin()` могут вернуть false независимо от реального пользователя. Если нужны DOM-узлы, обеспечь обе готовности. Страница вне фрейма приложения не даёт валидный BX24-контекст; не подставляй в неё административный токен для обхода. Сам факт готовности библиотеки не заменяет серверную авторизацию действий.

**Проверка на стенде:** Отложенная инициализация: UI не принимает false до init за реальный отказ в правах.

[Официальный контракт](https://apidocs.bitrix24.ru/sdk/bx24-js-sdk/system-functions/bx24-init.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K35 — Установка приложения и первый запуск пользователя — разные этапы

Для приложения с интерфейсом завершай установочный мастер `BX24.installFinish()` после успешных обязательных регистраций и сохранения настроек. До этого event.bind/placement.bind могут быть успешны, но события и встройки ещё недоступны; сверяй `app.info.INSTALLED`. Не вызывай finish до инициализации библиотеки. Отличай мастер установки от обработчиков первого пользовательского запуска `BX24.install`: там finish продолжает цепочку и должен вызываться даже при ошибке настройки, иначе init не продолжится. У REST-only приложения без интерфейса установка завершается автоматически — JS-функция во внешнем PHP-обработчике не нужна.

**Проверка на стенде:** До/после завершения мастера сравнить INSTALLED и доставку; ошибка первого запуска не блокирует цепочку init.

[Официальный контракт](https://apidocs.bitrix24.ru/sdk/bx24-js-sdk/system-functions/bx24-install-finish.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K36 — Контекст встройки не является разрешением на объект

`BX24.placement.info()` синхронно возвращает код точки встраивания и options текущего контекста, не принимает callback. Читай после готовности библиотеки. Поля options зависят от конкретного placement: нельзя считать, что всякая встройка передаёт ID сделки одинаковым ключом. На своём backend проверяй тип объекта, ID и доступ авторизованного пользователя; браузерный контекст можно подменить. Для возможностей взаимодействия с родителем выясняй интерфейс конкретной точки, не вызывай команды от другой встройки по совпавшему названию.

**Проверка на стенде:** Подмена ID в запросе виджета не открывает чужой объект; неподдерживаемый placement обработан явно.

[Официальный контракт](https://apidocs.bitrix24.ru/api-reference/widgets/ui-interaction/bx24-placement-info). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.

## K37 — Общие и пользовательские настройки REST-приложения

`user.option.set` сохраняет настройки пользователя, чьим токеном вызван метод, в контексте приложения; передача произвольного USER_ID не делает настройку чужой. У серверного REST-only приложения это часто установивший его пользователь. Для общих настроек нужен `app.option.set` с соответствующими правами администратора ([контракт](https://apidocs.bitrix24.ru/api-reference/common/settings/app-option-set.html)); эти настройки общие, не персональные. Передавай options объектом: изменяются только перечисленные ключи; пустая строка оставляет ключ, а не удаляет. Не используй ключи next/total, которые REST может вынести из result. Общие настройки не подходят для секретов отдельных пользователей.

**Проверка на стенде:** Два пользователя: персональные значения изолированы, общая настройка едина; непереданный ключ сохранён.

[Официальный контракт](https://apidocs.bitrix24.ru/api-reference/common/settings/user-option-set.html). Сверка документации: 2026-11-01; установленное ядро и runtime этого сценария здесь не проверены.
